# GameMod: injected C/ASM rules

This folder holds the game-side half of the mod. It is compiled by devkitPPC via `WWOnline.Patcher`, and **only when the user asks** (see the root CLAUDE.md).

## Key rules
1. **`tww-decomp/` is the authority.** Look up every offset, proc id, flag and behaviour there, and cite it in a comment (`d_a_player_main.cpp:1234`, `d_save.h`). Never guess.
2. **Use offset macros, never struct fields.** `include/ww_structs.h` offsets are wrong (GCC vs Metrowerks padding). Use or add a macro in `include/ww_inlines.h` (`DAPY_LK_MCURPROC(link)`, `GAMEINFO_PLAYERSTATUS(&g_dComIfG_gameInfo)`, ...) with the decomp field in a comment. This applies to `g_dComIfG_gameInfo` too: raw offsets via `GAMEINFO_*` macros only.
3. **Put scratch/sync addresses in `src/puppet_link/puppet_shared.h`, never inline.** It is the memory map shared with C#: the client generates `PuppetLayout.g.cs` from its integer `#define`s. Put one integer literal in each `#define` and keep derived values as macros. Any change there needs a re-patch, which the build stamp enforces.
4. **Keep the hook tiny and put new logic in the REL.** See the table below.
5. **Guard global state.** `daPy_lk_c` code assumes `this` is the local player. Wrap `playerInit`/`playerDelete` (`puppet_saveGlobals`/`puppet_restoreGlobals` in puppet.c) and every proc init/execute (`puppet_guardBegin`/`puppet_guardEnd` in puppet_execute.c) so a puppet never changes the local player's status bits, event flow, hearts, magic, rumble, BGM, HUD or Z-target. Any new call into player code goes inside a guard.
6. **Watch the ARAM budget.** All of RELS.arc stays in ARAM for the session, and too much growth makes the first play scene's ARAM mount fail (`d_s_play.cpp:3439`; about 1 MB is free in vanilla, see `ElfToRelConverter.MaxRelsArcGrowthBytes`). The build guards 64 KB of growth. The puppet REL and the profile list are stored Yaz0 like every vanilla REL, only the puppet REL may be replaced, and the other RELs keep their compression (`RelsArcReplaceTests`). The v0.1.0 REL is 87,336 bytes raw and 35,383 bytes Yaz0, so RELS.arc grows by a little over 35 KB (entry + alignment on top). Keep the REL lean anyway.

## The two pieces
| | Puppet REL (`puppet.c` + includes) | Draw hook (`link_draw_hook.c`) |
|---|---|---|
| Built by | `BuildRelStep`: C -> ELF -> REL module 0x58 -> RELS.arc | `HookAsmGenerator`: C -> linked at 0x80286000 -> `link_draw_hook.asm` (generated, do not edit) |
| Runs | as actor proc 0xB5 (profile slot redirected to `g_profile_PUPPET`) | from `daPy_Draw` (branch at 0x80108204) |
| Size | limited by the ARAM budget | **0x4C8 bytes max**: live code starts at 0x802864C8 (`HookAsmGenerator.CodeLimit`) |
| `.rodata` | fine: string/float literals, `OSReport` | **none**: no string or float literals (floats via IEEE-754 ints in a scratch word from puppet_shared.h) |
| Also | new sections go in `ElfToRelConverter.AllowedSections` | register allocation is fragile, so add nothing per-frame here |

Code organisation: the REL is one translation unit: `puppet.c` `#include`s every other `puppet_*.c`, and holds the profile, create/delete and a thin dispatch. `puppet_execute.c` holds network state, the proc/animation state machine (including the climbing procs: ledge grab / hang / shimmy / climb-up, ladders, vine walls, sidle, push/pull, crawl), collision and the global guard. `puppet_draw.c` holds rendering. `puppet_worldsync.c` holds the REL side of world sync (item despawn, and a waiting boss Heart Container once the stage's STAGE_LIFE bit is set: another player took theirs). `puppet_liveworld.c` catches create-only actors up with bits other players set (delete, then re-create in the actor's own layer, doors included; table-driven, see docs/live-world.md §0; never write a door's lock byte: that froze the game, §0.1). It runs from the puppet's draw, after every execute of the frame, never from an execute: the player stores raw actor pointers in event orders. It is built with `#pragma GCC optimize("no-shrink-wrap")` to save REL space. `puppet_appearance.c` holds per-Link outfit + tunic colour. `puppet_sharedanm.c` keeps each puppet's animator pointers out of Link's shared model data (see Shared model data below). `puppet_boat.c` draws the peer's King of Red Lions (hull + head from the "Ship" archive in the puppet's own heap, posed on the local sea) and seats the puppet in it. Its sail cloth runs the game's own daGrid_c code (`ho_move`, `daHo_packet_c::draw`) on an imitation grid in that heap, with `l_ship` pointed at a stub only during `ho_move`, and is recoloured per peer by swapping new_ho1's palette offset around our packet's draw. The peer's cannon / crane (plain models on the mast joint, aimed from the slot's `PUPPET_BOAT_CANNON_*` / `PUPPET_BOAT_CRANE_*` word) and the crane's rope (a 2-point `mDoExt_3DlineMat1_c` hanging straight down, not simulated) and hook are drawn while their `mPart` is out; nothing fires or salvages. Never spawn a second `daShip_c`: it takes over the global ship pointer and writes the local player's sail state. `puppet_nametag.c` draws the peer's name above the puppet (see below). `puppet_held.c` mirrors the peer's held item, item procs, upper-body item anims and aim, and draws a held boomerang / carried bomb from the "Link" archive in its own heap (docs/held-items.md). Never let `makeItemType` run for the boomerang, hookshot, grappling hook or bomb bag on a puppet (it spawns actors bound to the local Link), and never let `checkItemAction` see a puppet's BOOMTHROW (it throws a NULL boomerang). `puppet_fx.c` makes other players' projectiles real (see below). `puppet_seachart.c` draws the other players on the sea chart: the menu runs while no actor does, so the required patch `src/patches/seachart_players.asm` calls it through `SEACHART_FN_ADDR` from `dDlst_FMAP_c::draw`, after the chart's screen; it redraws Link's own marker picture per player (moved, turned, tinted) and puts it back. The pointer is published at every puppet create and cleared at the last delete, before the REL is unlinked. `puppet_anmmirror.c` handles every proc `puppet_applyProcInit` has no case for (its `default:`): the puppet enters WAIT and plays the peer's own body bcks (under[0..1], upper[0..1] with frame, rate, start/end/loop and blend ratio), face btp/btk and hand shapes from the anim mirror block (`PUPPET_ANM_*`). It keeps mCurProc WAIT (a relabel would run a never-started proc's commonProcInit exit code) and re-inits WAIT itself when the peer goes back to WAIT. Bcks load into the ONE shared 0xB400 body anm buffer only where earlier tracks left the region free, capped at its end, never into upper[2]'s (+0x9000, puppet_held.c's). A proper `case` added to the switch takes precedence automatically.

## Memory map
- `0x80286000..0x802864C7` is hook code only, not free space.
- `0x803FCF20..0x803FCFA7` is the DOL's `.sbss2`, which holds live game constants. **Never write here.**
- `0x803FCFA8..0x803FD1FF` (`SCRATCH_REGION_START/END`) is our scratch/sync region. It is mapped word by word in `puppet_shared.h`, which also documents the layout. It is the zero-filled start of DolPatcher's Text2 section (reloaded, so zeroed, at every boot): the required `seachart_players.asm` puts code in free space, so every patched game has Text2, and the boot stack sits above the custom code, which starts at `0x803FD200`. (Before that patch, a build with no free-space patch left it the never-reached bottom of the vanilla boot-thread stack, which survives a soft reset: hence the boot stamps on the heap blocks.)
- Game-heap blocks hold what doesn't fit in scratch; scratch only holds their pointers. Each is allocated once by the REL, never freed, adopted by the next REL and boot-stamped (see 2D / name tags below): names (`PUPPET_NAMES_*`, 0x58 bytes), sea chart (`SEACHART_*`, 0x90), live world (`LIVEWORLD_*`, 0x4C), projectile events (`PUPPET_FX_*`, 0x3F0), anim mirror (`PUPPET_ANM_*`, 0x160) and the local Link's recoloured tunic (`LOCAL_APPEARANCE_BLOCK_ADDR`).

The scratch region today (writer: hook = link_draw_hook.c, REL = puppet_*.c, C# = the client):

| Range | What | Writer |

So 4 words are free: `0x803FD1D0..DF`. A new block of state belongs on the game heap behind one of them, like the blocks above.
- Game globals (stage, room, save, event flags) are reached via `g_dComIfG_gameInfo` + `GAMEINFO_*` macros in C, and via `GameMemoryAddresses` (GameInfo/Play + decomp offset) in C#.

## C pitfalls
- **Inline functions have no body.** Calling a WW inline jumps to a fake address. Do what it does by offset instead, e.g. `(MTX34*)((u8*)model + 0x24)` for `getBaseTRMtx`.
- **Calling game functions:** functions are named `Class__method` in `include/ww_functions.h`, with addresses in `include/ww_linker.ld`. Globals are in `ww_variables.h`. Only call what is in the linker script.
- **Shared model data:** the puppet is built by the stock `playerInit` from Link's shared archive model data, and `daPy_lk_c` writes pointers to its own heap objects into it: the face materials' `J3DMaterialAnm`, btk/brk animators in the effect and item models' material anm slots, joint 0's `mMtxCalc`. `puppet_sharedanm.c` owns all of that. Every puppet create / execute / draw is a window (`puppet_shanmBegin`/`End`): the animator slots of every "Link" archive model are snapshotted, the puppet's own values go in, and afterwards whatever it changed goes into its swap list and the local Link's values come back. So outside those windows the shared data is exactly the local Link's (a puppet's J3DMaterialAnm left there crashed `J3DJoint::entryIn` once the puppet was deleted). Any new call into player code that registers animators must run inside such a window. A window costs ~23k instructions (flattened tables, unrolled copy/compare), so open one only where player code actually runs: parked puppets and undrawn slots skip it. Content swaps (linktex ResTIMG, shape visibility, anm frames) are still set right before the puppet's `mDoExt_modelEntryDL` and restored right after (see puppet_draw.c); that works because texture headers and material anms are read when the entry builds the model's differed display list (`J3DModel::diff` -> `loadTexNo`, `J3DJoint::entryIn`), not when the packets execute.
- **Debugging a crash:** with the JUTException screen up, `python scripts/dolphin-crash-context.py <dolphin pid> tww-decomp/config/GZLE01/symbols.txt` prints PC/LR/registers and the symbolised stack from the live Dolphin. `python scripts/dolphin-link-anm-check.py <pid>` lists every animator pointer in Link's shared model data that isn't the local Link's (use-after-free suspects); the REL logs `[PUPPET] shared anm ...` on create/delete (`into-puppet=` must be 0). Both scripts only read emulated RAM.
- **Appearance:** outfit and tunic colour both live in the linktexS3TC header (colour = a recoloured copy of the texture; the body TEV never uses the material colour). The REL owns that header for the local Link while it is loaded (`puppet_appearance_tick`), and each puppet swaps its own in around its entry. The C# client only publishes `LOCAL_APPEARANCE_WORD`; never write Link model data from C#.
- **Display packets:** each puppet owns its packets (`PUPPET_class.packets`). Entering one `J3DPacket` twice makes the draw list cyclic, which hangs the game.
- **2D / name tags:** `puppet_nametag.c` projects a point above the puppet (`mDoLib_project`) in its draw and enters its own `dDlst_base_c` (vtable in the REL: `{0, 0, dtor, draw}`) in the 2D opaque list, like the HUD. Its draw runs in the painter's 2D pass: `J2DOrthoGraph::setPort` on the current graf port, then the message font `mDoExt_font0` (held for good since boot, d_s_logo.cpp:576; read it, never `mDoExt_getMesgFont`, which counts a reference) through its vtable, and `setPort` again after. Safe because the painter runs at the start of the next frame, before deletes. Names come from a game-heap block the REL allocates once and never frees (`PUPPET_NAMES_*`), so C# can write it without racing a free. The block is stamped with `__OSStartTime` and both sides use it only while that matches: its pointer (and bytes) survive a soft reset, which recreates the game heap. `puppet_bootBlock`/`puppet_bootBlockCreate` (C) and `BootStampedBlock` (C#) do this for any such block (the live-world block uses them too). Hidden when the game hides its HUD (`m2dShow`, events, pause menu, telescope, Picto Box).
- **Projectiles** (`puppet_fx.c`, SharedProjectiles rule): once per frame (from every puppet's execute, parked ones too, before the guard) the REL watches the LOCAL Link's bombs (`mActorKeepGrab` holding a STATE_1..3 `daBomb_c`) and the boat's cannonball (the one BOMB with exactly the ship's params the frame `daSFLG_SHOOT_CANNON` is set) and writes throw / pickup / explode / gone / cannon events to the events block's outbox; C# relays them. Peers' events come back through the inbox and become real `daBomb_c`s via `fopAcM_fastCreate` (a lit STATE_1 bomb with the sender's velocity and fuse, the ship's STATE_4 cannonball, or a STATE_0 explosion). Every copy: carries `FX_BOMB_PRM_COPY` in its params (a free prm bit) so no tracker reports it back; has `field_0x6F0` cleared (else its explode/delete call the LOCAL Link's `decrementBombCnt`); has the AT's VsPlayer bit cleared (it hurts enemies, walls and switches, never the local Link, his ship or puppets); has its fuse held at 3 until the sender's EXPLODE, which snaps it to the sender's position and calls `procExplode_init` (only while it is as spawned: carried, swallowed or given a lower fuse by the game, it becomes this world's bomb). The local Link is `play.mpPlayerPtr[0]`, never `dComIfGp_getPlayer(0)` (an NPC while the player controls Medli, Makar, a seagull or Hyoi). Every event carries the projectile's own `current.roomNo`, so the client scopes it to the room where it happened; a copy that became this world's bomb ignores the sender's later throw / pickup / explode / remove. (The client drops peers' events during a minigame.) Never give a copy STATE_3 (the bag bomb: it binds to the local Link's bomb count). Arrows: the nocked arrow (`mActorKeepEquip`) leaving the bow with param 1 is reported once; a peer's becomes a real `daArrow_c` made detached (`fx_spawnArrow`): the peer's type in `m_keep_type` and the local magic raised to 2 only around the synchronous create, then moved out of the local Link's hand, CO off (no +1 arrow pickup), `mCurrProcFunc` = procMove and `arrowShooting()` (its AT capsule's only registration that frame: a fastCreate'd actor first executes the next frame). Never set a copy arrow's param to 1: `procWait` would spend the local magic and its effect child would set the local Link's USE_ARROW_EFFECT. The block (`PUPPET_FX_*`, pointer at `PUPPET_FX_PTR_ADDR`) is allocated and boot-stamped like the names block.
- **Peer equipment** is presented by swapping the save's select-equip bytes inside the guard. The swap is seqlocked for C# (`PUPPET_EQUIP_SWAP_SEQ_ADDR`), and End restores a byte only if it still holds the peer value.
- **Delete path:** `daPuppet_Delete()` must call `daPy_lk_c__playerDelete()` or room transitions crash. Bounds-check slot indices against `PUPPET_MAX_SLOTS`. NULL-check `polyInfo` / `mpJoints`.
- **Globals** like `l_puppetFollowState` are safe only because GameCube actors run single-threaded. Save and restore them per puppet.
- Compile flags (`DevKitPpcToolchain`): `-mcpu=750 -std=c99 -fno-inline -Wall -Og -g -fshort-enums -fno-jump-tables`. `-fno-jump-tables` avoids R_PPC_REL32 relocations. `-g` and `.eh_frame` never reach the REL (only `ElfToRelConverter.AllowedSections` are copied). `-Os` was measured: 20% smaller raw but only ~1.5 KB smaller once Yaz0-compressed, a new codegen for every function, and it needs libgcc's `_restgpr_*_x` and the DOL's memset/memcpy, so the REL stays `-Og`.

## ASM patches (`src/patches/`)
WW_Hacking_API style (`.open "sys/main.dol"`, `.org <addr>`, `.close`). Every `.asm` file directly in `src/patches/` is a **required** patch picked up by `AssemblePatchesStep`: `use_extra_memory.asm` (48MB, which also needs bi2.bin) and the generated `link_draw_hook.asm`.

`src/patches/optional/<id>.asm` are **player-selectable** patches (skip intro, betterww QoL, vanilla bug fixes). Each file's `; @name / @description / @category / @default / @match / @multiplayer / @credit` header is its catalogue entry (single source of truth); `@conflicts` and `@edit` (BMG / file / dzb edits in C#) are optional. All of them are assembled every build; only the selected ones are applied. See `docs/optional-patches.md`. Rules for them:
- Never write `.sbss2`, the scratch region or the hook (enforced by `GamePatchApplier.Validate` and tests).
- Custom code goes in main.dol `@NextFreeSpace`, which starts at `SCRATCH_REGION_END` (`free_space_start_offsets.txt`, enforced). Prefix global labels with the patch id: every optional patch is assembled in one symbol table.
- REL patches (`.open "files/rels/x.rel"`) may not use `@NextFreeSpace` or need new relocations: a `bl` into main.dol must replace a call that already had a main.dol REL24 relocation (it gets re-targeted). Put the main.dol block before the REL block so its symbols exist.
- Two patches writing the same bytes must declare `@conflicts`.

`free_space_start_offsets.txt` sets where free space begins in each file.
